# Postgres migrations

Companion migrations for the Postgres adapter (`PostgresAdapter`). The
canonical schema lives in `../migrations/` as SQLite/D1; this directory
mirrors each numbered migration translated for Postgres semantics.

## Translation rules

Mechanical rewrites from SQLite → Postgres:

| SQLite | Postgres |
| --- | --- |
| `TEXT` | `TEXT` (unchanged) |
| `INTEGER` | `BIGINT` |
| `REAL` | `DOUBLE PRECISION` |
| `?` placeholders | `$1`, `$2`, … (rewritten by `PostgresAdapter` at runtime — DDL files use `?` only if they're parameterized, which they shouldn't be) |
| `AUTOINCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` |
| `INSERT OR REPLACE` | `INSERT … ON CONFLICT (…) DO UPDATE SET …` |
| Stored `TEXT` with JSON | `JSONB` (always; the dashboard read paths can leverage indexed JSON queries on Postgres) |

## Numbering

Files MUST share the numeric prefix of their D1 sibling so the
migration runner can ensure parity. If `004_logs.sql` exists in
`../migrations/`, this directory MUST contain `004_logs.sql` as well.
A CI check will refuse to merge PRs that break parity.

## What's translated

The first three migrations are translated as a proof of the pattern.
The remaining migrations are tracked in
[`docs/postgres-migration.md`](../../../../docs/postgres-migration.md);
they'll land alongside the first hosted-Postgres deployment.

## What's NOT translated

`009_projects_and_keys.sql` uses SQLite's `BLOB` type for the hashed
API key. Postgres uses `BYTEA` and the column-name rewrite is in
`009_projects_and_keys.sql` here (a non-mechanical translation; review
carefully when porting forward).
